# demand-forecasting-api

FastAPI service serving demand forecasts from a trained scikit-learn GradientBoosting model. Containerized with Docker, deployable to Azure App Service in one script.

Built as a portfolio demo of the FDE motion: here is a working solution, here is the business problem it solves, here is how to run it in your environment.

## Quickstart (local)

```bash

python scripts/train.py

uvicorn app.main:app --reload

```

## API Reference

### `POST /forecast`

Returns a demand forecast with confidence interval for a single product/store/date combination.

**Request:**

```json
{
  "product_id": "SKU-1042",
  "store_id": "STORE-07",
  "year": 2026,
  "month": 6,
  "day_of_week": 2,
  "week_of_year": 24,
  "is_holiday": false,
  "is_weekend": false,
  "temperature_c": 21.5,
  "promotion_active": true,
  "price": 4.99,
  "lag_7_demand": 142.0,
  "lag_14_demand": 138.0,
  "rolling_28_avg": 145.3
}
```

**Response:**

```json
{
  "product_id": "SKU-1042",
  "store_id": "STORE-07",
  "forecast_units": 187.4,
  "lower_bound": 142.1,
  "upper_bound": 232.7,
  "confidence": 0.847,
  "model_version": "1.0.0"
}
```

### `POST /forecast/batch`

Batch forecasting for up to 100 items in a single request.

```json
{
  "items": [ { ...forecast_request }, { ...forecast_request } ]
}
```

### `GET /health`

Returns model status, version, feature list, and training timestamp.

## Model

**Algorithm:** GradientBoostingRegressor (scikit-learn)

**Features (14):**

| Feature | Description |
|---------|------------|
| `product_id` | Product SKU (label encoded) |
| `store_id` | Store identifier (label encoded) |
| `year`, `month`, `week_of_year` | Temporal features |
| `day_of_week` | 0 = Monday, 6 = Sunday |
| `is_holiday`, `is_weekend` | Calendar flags |
| `temperature_c` | Ambient temperature |
| `promotion_active` | Whether a promotion is running |
| `price` | Current unit price |
| `lag_7_demand` | Actual demand 7 days prior |
| `lag_14_demand` | Actual demand 14 days prior |
| `rolling_28_avg` | Rolling 28-day average demand |

**Trained on:** 15,000 synthetic retail demand samples with realistic seasonality, promotion lift, price elasticity, and autoregressive components.

**Test set metrics:**

| Metric | Value |
|--------|-------|
| MAE | 20.1 units |
| RMSE | 28.9 units |
| MAPE | 7.3% |

**Confidence intervals:** 80% CI computed from model residual standard deviation on the held-out test set.

## Deploy to Azure

```bash
# Authenticate
az login

# Deploy (creates resource group, ACR, App Service plan, Web App)
chmod +x scripts/deploy-azure.sh
./scripts/deploy-azure.sh
```

Override defaults via environment variables:

```bash
RESOURCE_GROUP=my-rg \
APP_NAME=my-forecast-api \
LOCATION=westus2 \
./scripts/deploy-azure.sh
```

The script provisions:
- Azure Container Registry (Basic tier)
- App Service Plan (Linux, B1)
- Web App for Containers with health check on `/health`

## Design Notes

**Why GradientBoosting over a neural network?** For tabular retail demand data, tree-based ensembles consistently outperform neural networks at this sample size. GBRT handles mixed feature types natively, trains in seconds, and produces predictions that are easy to interrogate. The right tool for the problem.

**Why lag features instead of a time-series model?** Adding lag demand as a feature lets a standard supervised learner capture the autoregressive component without the stationarity requirements and data volume that ARIMA or Prophet need. Simpler, faster, and easier to deploy at an API endpoint.

**Why 80% CI instead of 95%?** In retail demand planning, a 95% CI is often too wide to be operationally useful. An 80% CI tightens the planning band and is more honest about the model's actual precision at this scale.
